一条记忆的一生

从一次 run 完成，到一条跨会话事实落库，中间隔着九道闸门和一次一次性模型调用。 这张图只讲记忆链路本身：谁触发、读到什么、写下什么、什么情况下什么都不写。

先回答：每次会话结束都会提炼吗

不是等会话结束，而是每次 run 正常完成就试一次。触发点在 AgentService 的 run.completed 分支——消息落库完成即回调一次蒸馏，不等会话关闭。

但"试一次"不等于"写一条"：同一会话有 5 分钟冷却、并发直接丢弃，蒸馏读的是 至今全量转写（不是增量），所以第一次之后的每次执行大多只是在跟已有记忆做去重。

另外三个前置条件：转写 ≥ 600 字、用户发言 ≥ 2 轮、lite 档已配置。缺任何一个都不写，且全程静默。

01

写入链路

run.completed → 去重 → hippo

五条泳道是这条链路上真正被调用到的五个东西。虚线是回传/只读，粗线是"世界被改变"的那一步： 只有 remember 会真的写进记忆库，其余全是判断。

02

实际节奏

一次 30 分钟的会话里会发生什么（示意）

因为触发点是"每次 run 完成"，一次多轮会话会产生很多次尝试；5 分钟冷却把实际执行压到稀疏几档， 而去重让后面几次执行基本写不进东西。这就是为什么记忆库长得像清单，而不是聊天记录备份。

阴影是首个 5 分钟冷却窗口：窗口内的后续 run 完成只记一次尝试，不执行。之后的每次执行读到的仍是"至今全量转写"， 里面的旧事实已经在库里，被包含式去重挡掉——所以写入几乎只发生在最初一两档，之后归于平静。

03

九道闸门

任何一道不过，就什么都不写，而且不报错

闸门顺序即代码顺序。右列是 DistillOutcome.skipped 的取值——这些值只会进日志，不会回到对话里。

04

落库的那条长什么样

hippo-memory 行（MEMORY_ENVELOPE）

一条记忆不是一句话，是一个带强度、半衰期、作用域和溯源的信封。注意 tags 里混着一半用户看不见的检索键。

三个反直觉的点

标签是双份的。中文内容会追加 jieba 分词转写（用户 → zh7528_6237）进 tags，只为让 BM25 命中；读取时再统一剔除，用户只看到原始标签。

召回不会变强。markRetrieved 与 MemoryService.feedback 目前都没有产品侧调用点——检索不计分，条目强度只会被整理回合衰减。这是接进来但没接线的一段。

没有对外写入口。网关只暴露 status / entries / search / delete 四个端点；写入只能来自 agent 工具或蒸馏，避免绕过提炼规则灌数据。

05

读取链路

「上次说的那个方案」→ 命中 → 进上下文

读取没有自动注入这一步：靠系统提示词里的两条行为指引，让模型自己决定要不要检索。 检索为空时它被要求如实说"没有相关记忆"，而不是编一个。

06

维护链路

不在请求链上，每 6 小时跑一次

写入是事件驱动的，整理是定时驱动的。这一环决定记忆库会变成"越用越准的清单"还是"越用越乱的日志"： 衰减让久不用的条目退场，合并把零散情景并成语义条目，冲突留在清单里等人判断。

三个硬约束：noShare（不向全局库复制，单租户产品不需要）、extraction.enabled = false（关掉库自带的 LLM 事实提取， 保证整理全程不出网）、并发丢弃（一次整理可能持续数秒，重入直接放弃）。
